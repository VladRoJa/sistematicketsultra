## Hallazgo de auditoría: diferencia de alcance entre E2 y E3

Revisión de código en `backend/app/routes/inventario_solicitudes_routes.py::_actor`:
`_GLOBAL_ROLES` aún incluye `MANTENIMIENTO`, `SISTEMAS` y `TECNICO`,
además de roles administrativos. Por tanto, el listado/creación E2 puede ser
más amplio que la regla E3 aprobada para autorizaciones. En cambio,
`backend/app/utils/inventory_correction_permissions.py` exige en E3
un grant explícito y la intersección de `usuario_sucursal` para mantenimiento
y coordinación, sin permitir autorización regional de `MASTER_FIELD`.

**No confundir ambas capacidades.** Cierre de QA E2 pendiente de decidir
explícitamente el scope para MANTENIMIENTO, SISTEMAS y TECNICO; no cambiar
`_actor` sin evaluar compatibilidad con el piloto E2. La extensión de alcance
E2 no da por sí sola facultad de aprobación E3, ya protegida con guard
independiente.

### Verificación de solo lectura en PostgreSQL productivo (sin tokens ni writes)

```sql
BEGIN TRANSACTION READ ONLY;

-- Estado actual de todas las solicitudes y cuentas autoras.
SELECT s.estado, s.tipo, s.sucursal_id,
       COUNT(*) AS total
FROM inventario_correccion_solicitudes s
GROUP BY s.estado, s.tipo, s.sucursal_id
ORDER BY s.sucursal_id, s.tipo, s.estado;

-- Excepciones observadas para autores técnicos no administrativos.
-- 0 filas NO demuestra que el guard E2 deniegue otra sucursal:
-- únicamente que no se observan solicitudes ya creadas fuera del alcance.
SELECT u.id AS usuario_id, u.username, u.rol, s.sucursal_id,
       COUNT(*) AS solicitudes_fuera_de_asignacion
FROM inventario_correccion_solicitudes s
JOIN users u ON u.id = s.creado_por_usuario_id
WHERE UPPER(TRIM(u.rol)) IN ('MANTENIMIENTO','SISTEMAS','TECNICO')
  AND NOT EXISTS (
      SELECT 1 FROM usuario_sucursal us
      WHERE us.user_id = u.id AND us.sucursal_id = s.sucursal_id
  )
GROUP BY u.id, u.username, u.rol, s.sucursal_id
ORDER BY u.id, s.sucursal_id;

-- Comparar propuestas pendientes con stock oficial sin mutación.
SELECT s.id, s.tipo, s.sucursal_id, s.inventario_id,
       s.creado_por_usuario_id, s.estado,
       s.baseline_canonico ->> 'stock' AS stock_baseline,
       stock.stock AS stock_oficial_actual,
       CASE
         WHEN s.tipo = 'UNREGISTERED_FIND' THEN 'SIN_REFERENCIA_AUN'
         WHEN (s.baseline_canonico ->> 'stock') IS NULL THEN 'SIN_BASELINE_STOCK'
         WHEN stock.stock IS DISTINCT FROM
              (s.baseline_canonico ->> 'stock')::integer THEN 'STALE'
         ELSE 'COINCIDE'
       END AS diagnostico
FROM inventario_correccion_solicitudes s
LEFT JOIN inventario_sucursal stock
  ON stock.inventario_id = s.inventario_id
 AND stock.sucursal_id = s.sucursal_id
WHERE s.estado = 'PENDING'
ORDER BY s.id
LIMIT 100;

COMMIT;
```

**Interpretación:** las consultas evidencian datos y discrepancias observadas, no prueban
por sí solas que los endpoints respeten alcance. Una prueba autenticada GET
con cuentas piloto y acceso cruzado denegado deberá verificar el control real
sin enviar credenciales al chat ni modificar stock.

**Corrección preparada en la rama E3 (sin desplegar):**
`backend/app/routes/inventario_solicitudes_routes.py::_actor` consulta
`usuario_sucursal` para los tres roles técnicos, igual que para
`SR_MANTENIMIENTO`; no suma `users.sucursal_id` como fallback y deniega
si no hay asignaciones. Se mantiene la decisión E3 en un guard independiente.

**QA sintético:** test E2 en PostgreSQL temporal comprueba GET/lista, GET por ID,
POST autorizado y denegado en sucursal primaria fuera de la relación M:N,
falta de asignaciones y no mutación de stock/maestro V1. CI de última revisión
necesario antes de considerar cerrado este cambio.

**Pendiente separado:** `AUX_MANTENIMIENTO` usa todavía primaria en E2 por el
