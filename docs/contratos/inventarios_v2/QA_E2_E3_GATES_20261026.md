## Bloqueador de experiencia: coordinación Yuliana

El guard E2 de `inventario_solicitudes_routes.py::_actor` actualmente excluye el rol `COORDINADOR_MANTENIMIENTO` de listar/crear E2. E3 permite a coordinación ser **candidata a decidir** si dispone de acción E3 explícita y sucursal asignada, pero eso **no implica** abrir E2 ni permitir crear propuestas.

**Antes del frontend E3:** habilitar **bandeja de revisión independiente** con un GET E3 autenticado, filtrado server-side por permisos de revisión y `usuario_sucursal`, más GET de detalle E3 sin IDOR. Nunca quitar el guard E2 global para resolver esta necesidad. El listado E3 no puede mostrar datos de sucursales fuera de competencia ni confiar en un checkbox para autorizar.

| Escenario | Resultado esperado |
|---|---|
| ADMICORP (#47) abre consulta E2 de ULTRA DEMO #1/#2 | E2 accesible en ámbito corporativo; sin cambio de stock por consultar |
| ADMICORP intenta autorizar su propia solicitud | **403** aun si tiene grant global E3 |

| MANT_YULIANA (#91) intenta E2 `GET /solicitudes` legacy | **403** vigente; deberá usar futura bandeja E3 cuando exista grant |
| Regional o GERENTE invoca E2 o E3 por API directa | **403** (o 404 sin fuga en detalle) hasta E5 |
| Solicitud stale o lote mixto | **409**, ningún ajuste ni decision parcial |
| Aprobación NO_LOCALIZADO sin resolución | **422**, oficial intacto |
| Hallazgo con `CREAR_NUEVO` o código de otro aparato | **422/409**, sin alta ni vínculo |
| Reintento mismo UUID/actor/payload | **200 replay**, sin doble efecto |

Las pruebas de autorización que impliquen stock deben usarse **solo en PostgreSQL temporal**, nunca en los registros sintéticos persistentes de ULTRA DEMO. Los registros #1/#2 creados por ADMICORP no son candidatos válidos para una aprobación de sí mismo; sin otro autorizador asignado a ULTRA DEMO no hay aprobación legítima.
